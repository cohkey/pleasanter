# 通知ログの表示

更新日：2026/11/09

通常時は条件が成立したルールだけ、通知ID・条件一覧・実際に評価した条件のJSONを表示する。不成立ルールの詳細は出さず、終了時の件数にまとめる。空行は挟まない。

## 通常時の例

ステータス0000→0100・電圧6kV。候補N002・N001・N999のうちN002だけ成立し、通知対象が未設定の場合。

```text
----- 通知ID: N002 -----
通知条件: 2件
パターン1 / denatsu / IN / 比較値: 6kV,20kV
パターン1 / status / FROM_TO / 比較値: 0000,0100
{"field":"denatsu","operator":"IN","value":"6kV,20kV","columnName":"ClassE","modelValue":"6kV","hasChange":false}
{"field":"status","operator":"FROM_TO","value":"0000,0100","columnName":"ClassB","modelValue":"0100","changedValue":"0100","hasChange":true}
条件成立: true
通知対象が未設定のためスキップ
----- 通知処理終了: 候補3件 / 成立1件 / 不成立2件 -----
```

成立ルールについては、既存の通知対象・店所・組織・最終To / Cc / Bcc・件名・本文も引き続き表示する。送信無効時は`送信無効のため送信していません`と表示し、送信成功を表示しない。条件成立数は送信成功数ではない。

## デバッグ設定

モジュール先頭の設定を切り替える。送信可否を設定する`SEND_ENABLED`とは独立している。

```js
const NOTIFICATION_DEBUG = false; // 通常運用
// 調査時のみ true にする
```

trueの場合は、従来のchangedFields・候補一覧・不成立ルールの区切り・条件一覧・評価JSON・成立結果も出力する。通常時と同じJSON形式と取得順・評価順を保つ。

例えば上の例では、N002の後に以下のN001の詳細が入り、その後にN999の詳細も表示する。

```text
----- 通知ID: N001 -----
通知条件: 2件
パターン1 / denatsu / NOT_IN / 比較値: 6kV,20kV
パターン1 / status / FROM_TO / 比較値: 0000,0100
{"field":"denatsu","operator":"NOT_IN","value":"6kV,20kV","columnName":"ClassE","modelValue":"6kV","hasChange":false}
条件成立: false
```

条件一覧は取得した全条件、JSONは実際に評価した条件だけ。短絡評価で未評価となった条件の結果は表示しない。

## 集計とエラー

- 候補数：見つかった有効な候補ルール数。リンク切れ・無効なルールは含めない。
- 成立数／不成立数：条件評価がtrue／falseで完了した数。通知対象未設定や送信無効でも、条件成立なら成立数に含める。
- 引き継ぎ情報なし・変更なし・候補なしでも、0件の終了集計を1回出す。
- エラーはデバッグ設定に関係なく表示し、同じ例外を再送出して処理を中断する。後続ルールの処理は進めない。
- 条件取得・評価中の例外では、そのルールの保存済み詳細も出して調査可能にする。リンク切れなど既存の警告・不正メール等の診断ログも常時表示する。

条件評価中の例外で、3候補のどれも判定が完了していない例：

```text
通知処理エラー: FROM_TOの比較値が不正です（変更前,変更後を指定）: bad
----- 通知処理中断: 候補3件 / 成立0件 / 不成立0件 / 未完了3件 -----
```

未完了数は候補数から成立数・不成立数を引いたもの。宛先解決などで中断した場合、そのルールの条件評価が完了していれば成立数に含まれる。終了・中断の表示はメール配送の成功を意味しない。

## 実装と検証

1ルール分の条件ログを一時保存し、判定完了後に成立またはデバッグ有効なら出力する。例外時にも保存済みログを出す。finallyで保存先を復元し、後続ルールへの混入を防ぐ。ログを出す目的で条件を再評価しない。条件検索・評価関数の判定式・AND/ORの短絡評価・メール送信処理は変更していない。

- Nodeテスト158件成功。通常／デバッグ、成立・不成立・0候補・例外、未送信表示、ルール間のログ混入を確認。
- 変更前コードとの比較で、既存28シナリオと複数ルールのAPI呼び出し・送信内容・例外・条件評価回数・順序が一致。デバッグ時の評価JSONも一致。
- 通知IDの防御除去・検索値の退行を検出する既存のチェックも成功。
- ローカル専用Pleasanter 1.4.23.3 / PostgreSQL 16で実更新。変更前・通常・デバッグの評価トレースが一致し、通常時は成立N001のみ、デバッグ時は不成立N999も表示。集計は候補2件／成立1件／不成立1件。
- 実更新の検証コピーだけcontext.Logをlogs.LogInfoに置換し、評価関数の呼出記録を追加。製品コードに検証用計測は含めない。サイト設定とレコード値は退避し、finallyで復元・一致確認。SEND_ENABLEDはfalseでOutgoingMailsは0件。実メール配送とブラウザ画面操作は未実施。

通知エンジン以外のcheckGMUser等のログは変更しない。
