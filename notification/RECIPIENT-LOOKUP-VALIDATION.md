# 通知対象・組織検索の未取得と修正

更新日：2026/11/06

## 確認した状況

利用先のログは「条件成立=true」「通知対象のToは取得済み」「店所＋グループからの組織が空」だった。したがって、直接の停止箇所はメールアドレス変換より前の組織検索である。

店所コードの画面表示が001でも、店所マスターを参照する分類項目の保存値はレコードIDになる。対象レコードのClassDと店所・組織表のClassAが同じ内部IDなら、そのIDをそのまま比較するのが正しい。表示コード001に変換する処理は追加しない。

## 再現した不具合

選択式・リンク式の分類項目へ単一文字列とExactMatchを渡すと、検証環境では検索が絞られず、初回200件だけが返った。コードはその200件を手元で照合するため、正しいレコードがそれより後にあると一致レコードが存在していても空配列になる。

通知対象の親ID検索にも同じ検索形式が残っていた。取得後の親ID照合は誤混入を防ぐが、検索時に取りこぼしたレコードを回復することはできない。

## 修正範囲

- getOrganizationCodesのClassA / ClassCを、JSON配列文字列＋ExactMatchMultipleへ変更。
- getNotificationTargetsのClassAも同じ形式へ変更。
- 取得後の店所・グループ・親ルールIDの完全一致確認は維持。
- 組織コードが空のときだけ、取得・照合・コード有無の件数を1行で記録。
- 通知ログの空行・区切り線先頭の改行を削除。

条件演算子、ルール・パターン評価、マスターの保存値、組織コードの項目対応、宛先の変換・重複排除、送信処理は変更していない。

組織コードの参照先は現行どおりDescriptionA。画面上の「組織コード」というラベルだけでは物理項目名を確定できないため、利用先のDescriptionAとの対応は別途確認対象である。

## 1.4.23.3での実測

専用Docker / PostgreSQL 16で、表示001の店所マスターと、その内部IDを保存するリンク式の店所・組織表を新設した。該当レコードを最古に置き、後から対象外200件を追加して、初回取得ページ外にある状態を比較した。検証用の組織コード2143938はDescriptionAに設定した。

| 店所・グループの分類設定 | 修正前の取得数・組織コード | 修正後の取得数・組織コード |
| --- | --- | --- |
| 自由入力 | 1件・2143938 | 1件・2143938 |
| 店所リンク＋グループ選択肢あり | 200件・空 | 1件・2143938 |

通知対象もリンク式の親IDで実検索した。修正前は対象外を含む2件、修正後は対象の1件だけを取得し、最終結果はどちらも `group=グリッドサービスG / addressType=To` だった。200件より後の通知対象の取りこぼしは単体テストで再現・修正確認した。さらに、リンク型の店所内部ID→組織コード2143938→ダミーのメール通知設定→To配列まで実行し、修正前はTo不足、修正後は `[User1]` と `test@example.invalid` を取得した。送信APIは呼び出していない。

実環境の検証は専用コンテナ・ループバックポート・専用DBボリュームの一致を確認するガード付きスクリプトで実行。新設テーブルはfinallyで削除し、元の専用検証SS設定とレコード値は復元して一致確認した。本番環境には接続していない。

これは同じ症状を生む検索不具合の再現結果であり、利用先の該当レコードが実際に初回200件外にあったことまで確認したものではない。既存の権限・サイトID・物理項目対応など、利用先固有の原因を全て確認したわけではない。

また、修正後も1回の取得で200件を超える「一致レコード全件」の巡回取得を新設したわけではない。未絞り込みの200件から照合していた問題を、DB検索で正しく絞るように修正している。

## 未取得時のログの読み方

```text
組織検索: 取得0件 / 条件一致0件 / 組織コードあり0件
```

検索でレコードを取得できていない。検索値・サイトID・アクセス権を確認する。

```text
組織検索: 取得1件 / 条件一致0件 / 組織コードあり0件
```

取得できたが、ClassAまたはClassCの保存値が入力と一致していない。

```text
組織検索: 取得1件 / 条件一致1件 / 組織コードあり0件
```

店所・グループは一致したが、参照するDescriptionAがnullまたは空文字。物理項目の対応を確認する。
