# 送信モードと通知メッセージ

更新日：2026/11/10

## 設定

```js
const NOTIFICATION_SEND_MODE = "TEST";
```

- TEST：条件・通知対象・宛先・件名本文まで通常どおり生成し、受付メッセージだけ表示する。notifications.New / notification.Sendは呼ばない。
- PRODUCTION：従来どおりnotifications.Newでメールを作成し、notification.Sendの戻り値で成功・失敗表示を切り替える。
- それ以外：設定エラーとして中断する。TESTやPRODUCTIONへ自動補正しない。

旧SEND_ENABLEDは廃止。設定値の参照はgetNotificationSendModeだけに集約し、処理開始時に検証して各ルールへ渡す。送信関数も未知の引数を本番扱いにしない。NOTIFICATION_DEBUGはログの詳細表示専用で、送信モードとは独立している。

## 表示例

通知対象の表示名が「ABCグループ」の場合。

TEST：

```text
【テスト】ABCグループ宛の依頼メールの送信を受け付けました。 ※実際のメールは送信していません。
```

PRODUCTIONでSendがtrue：

```text
ABCグループ宛に依頼メールを送信しました。
```

PRODUCTIONでSendがfalse：

```text
ABCグループ宛の依頼メールの送信に失敗しました。
```

受付・成功はalert-information、Send=falseはalert-error。Sendで例外が発生した場合は成功表示せず、従来どおり例外で中断する。標準Sendの戻り値がtrueでも、実メール配送や全メンバーへの到達を保証するものではない。

## 対象の表示名

固定組織は通知対象テーブル（SITE_IDS.targets）のClassBの静的選択肢から表示名を取得する。items.GetSiteで設定を読み、SiteSettings.ColumnsのClassB.ChoicesTextを参照する。宛先検索には保存値を使い、メッセージには表示名を使う。固定組織の許可コードは`1014797`・`1015247`・`1015246`・`TTA`。

店所連動組織・GMは「店所に紐づく」を付ける。客サ・グリサは次の指定名称に整える。この対応は表示専用で、宛先検索の値や対応表は変更しない。その他の店所連動組織はClassBの表示名に同じ接頭語を付ける。

| 対象区分 | ClassB保存値の例 | ClassB表示名の例 | メッセージに使用 |
| --- | --- | --- | --- |
| 店所連動組織 | グリッドサービスG（またはグリサ） | 任意 | 店所に紐づくグリッドサービスG |
| 店所連動組織 | お客さまサービスグループ（または客サ） | 任意 | 店所に紐づくお客さまサービスG |
| GM | 客サGM | 任意 | 店所に紐づくお客さまサービスGM |
| GM | グリサGM | 任意 | 店所に紐づくグリッドサービスGM |
| 固定組織 | 組織コード | ABCグループ | ABCグループ |

GM対応表のグループ名・コードや、展開先の第一〜第三の名前へ置き換えない。固定組織では対象テーブルで指定した表示名を使い、「店所に紐づく」は付けない。

Pleasanter 1.4.23.3の既定形式「保存値,表示名,略称,...」を扱い、表示名省略時は保存値が表示名となる標準仕様に合わせる。エスケープしたカンマ（\,）と改行コードCRLF/LF/CRを扱う。独自の選択肢分割正規表現や、動的・リンク選択肢の表示名解決は今回追加しない。

複数対象では、対象区分と保存値で同じ対象をまとめ、全対象の宛先名を「店所に紐づくお客さまサービスG、ABCグループ」のように列挙する。同じ対象をTo/Cc等に重ねて指定しても名前を繰り返さない。第一〜第三へ展開されたGMが複数でも、指定した「お客さまサービスGM」を表示する。

設定の取得失敗・選択肢にない値・動的選択肢等で名前を確定できない場合、保存コードを名前と推測しない。「指定された通知対象」、複数なら「指定された通知対象（N件）」という一般表現を使い、理由をログへ残す。一部だけ名前が判明しても、その名前で全対象を代表させない。表示名取得の失敗だけで、正常な宛先への送信を中断しない。

## メッセージを出すタイミング

1. 条件を従来どおり一度評価。
2. 成立したルールの通知対象を取得。
3. 既存の宛先取得・重複排除・To必須検証。
4. 件名・本文のテンプレート置換。
5. 表示名を取得。
6. TESTは未送信の受付表示。PRODUCTIONは既存の送信処理と結果表示。

不成立・対象未設定・宛先取得失敗・不正アドレス・本文生成失敗では受付／成功表示を行わない。複数ルールがある場合は各ルール単位で表示し、後続ルールが失敗しても先に完了したルールのメッセージは残る。全ルール成功を意味する一括メッセージは追加しない。

## 改行の確認結果

専用1.4.23.3でcontext.AddMessageに渡した改行が、context.MessagesのText内に保持されることは確認した。ただしAPIでのデータ確認はブラウザでの2行表示確認とは異なる。今回ブラウザ接続がタイムアウトし、実画面の改行表示は未検証。

公式フロントエンドはメッセージをjQueryの.textで設定する。HTMLのbrを文字列に混ぜても改行タグとして使えない。今回の既定は上記の1行表示とし、CSSは追加・変更しない。他のメッセージへの影響はない。

[公式AddMessage](https://pleasanter.org/en/manual/server-script-context-add-message)、[1.4.23.3の描画処理](https://github.com/Implem/Implem.Pleasanter/blob/Pleasanter_1.4.23.3/Implem.PleasanterFrontend/wwwroot/src/scripts/generals/message.js)。

### 実画面での確認手順

専用検証サイトだけで、更新後SSに次を登録し、ブラウザからレコードを更新する。

```js
context.AddMessage("一行目\n二行目", "alert-information");
```

下部メッセージが実際に2行か、画面幅による単なる折り返しではないかを確認する。API応答・JSON・開発者ツール上に改行があるだけでは成功と判断しない。

2行にならない場合に2行表示を採用するなら、検証用の専用クラスを付ける。

```js
context.AddMessage("一行目\n二行目", "alert-information notification-test-message");
```

```css
#Message .body.notification-test-message {
    white-space: pre-line;
}
```

通常のalert-informationの見え方が変わらないことも確認する。このCSSと2行版は確認手順であり、今回のコードには適用していない。確認後は検証用SS・CSSを元に戻す。

## 互換性と検証

条件・演算子・AND/OR・GM対応表・宛先解決・重複排除・通知APIのプロパティ設定は維持。表示名のためのサイト設定読み取りと、画面メッセージは追加・変更対象なので、変更前との比較では業務API・送信パラメータ・評価回数／順序・例外を照合する。

TESTでも既存の宛先設定エラーはそのまま検出する。GMグループコードの既存必須チェック等、宛先取得の仕様変更はこの変更に含めない。
