# sendRealtimeNotificationリファクタリングの検証

検証日：2026-11-04（日本時間）

## 原本との比較

写真転記版を基準に、リファクタリング前後で同じ入力を使って28シナリオを実行しました。Ccログの `CC:` → `Cc:` を除いて、処理結果、ログ、items.Getの呼び出し順、例外、通知APIへの引数が一致しました。別途Cc表記のテストを加え、全29テストが成功しています。

送信有効時の成功・失敗は、テスト内でのみ送信フラグを切り替え、通知APIのモックで検証しています。製品コードのSEND_ENABLEDはfalseです。

## 実Pleasanterでの回帰検証

専用Docker環境（Pleasanter 1.5.4.0 / PostgreSQL 16）で、APIによる実レコード更新とClearScript実行を確認しました。

| 検証 | 結果 |
| --- | --- |
| 前回と同じ17シナリオ | すべて期待した原本動作を再現 |
| ClearScriptでの条件評価・変換処理16アサーション | 成功 |
| 更新前の変更検出→context.UserData→更新後の引き継ぎ | 成功 |
| 条件成立→ルール→組織→宛先→件名・本文生成 | 成功 |
| To/Cc/Bccの重複排除 | 成功 |
| 独立したCc宛先 | `Cc: cc@example.invalid` を記録。`CC:` のログなし |
| 更新後通知のエラー時のデータ保存 | APIは422、レコードは更新済み。原本と同じ |
| OutgoingMails | 0件 |

実環境での観測のため、検証コピーにだけ更新前後の関数呼び出しを追加し、context.Logをlogs.LogInfoに置き換えて永続ログを確認しました。コード本体には実行呼び出しを追加していません。

対象シナリオは、原本のみでは通知を開始しないこと、変更なし、TO成立・不成立、無効ルール、ClassEの変更検出、ClassFだけの変更、本文のClassF参照、通知対象なし、To不足、不正な宛先区分、不正メール、不正ユーザIDの除外、配列でないユーザ指定、未定義テンプレート、宛先重複排除、および実エンジンでの境界条件検証です。

今回はリファクタリングのため、ClassEとClassFの使い分け、TOの値参照、例外時の処理中断、送信無効といった原本の仕様を保持しています。

## 検証していない範囲

- 実メール送信とSMTP接続、ユーザIDからの送信時アドレス解決。
- ブラウザの画面操作。
- 利用先のマスター・権限・大量データ・別バージョンでの動作。
