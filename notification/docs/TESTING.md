# 検証方針・変更時の確認手順

更新日：2026/11/05

## 1. 検証の分担

| 検証 | 保証する範囲 | 保証しない範囲 |
| --- | --- | --- |
| Node.jsの単体・回帰テスト | 条件評価、ルール分離、宛先生成、例外などのJavaScriptロジック | Pleasanterの検索・権限・列設定の実挙動 |
| 防御処理を外した検証用コピーのテスト | 親IDチェックの削除や検索値の退行をテストが検出できること | あらゆる不具合の検出 |
| Pleasanter / PostgreSQLの実更新 | 実ClearScript、items.Get、親ID列の設定、更新前後の引き継ぎ | 実メール配送、利用先の設定全般 |
| メール配送検証 | 実SMTP、ユーザIDのアドレス解決、実配送 | 現在未実施。モックの成功を配送成功と呼ばない |

テスト数ではなく、仕様上の不変条件と検証構成を記録する。原本との一致確認だけで業務仕様の正しさを判断しない。

## 2. 必須の不変条件

1. 対象ルールのResultIdとClassAが一致する条件だけが評価される。
2. 別ルールが同じパターン番号を使っても判定結果に影響しない。
3. 他ルールの条件で自ルールを成立・不成立にしない。
4. 他ルールの不正なFROM_TOを自ルールの評価に持ち込まない。
5. 同一ルール内のAND / OR、既存演算子、先頭ゼロを維持する。
6. 通知内容の生成成功と送信成功を区別する。
7. SEND_ENABLED=falseでは通知APIを呼び出さない。

## 3. 自動チェック

作業フォルダのルートから実行する。追加のnpmパッケージは不要。

```sh
node --check notification/sk-realtime-notification.js
node --test notification/test/realtime-notification.test.cjs
node notification/test/check-rule-scope-regression.cjs
```

通常テストは123件。最後のコマンドは別の「成功ケース2件」ではなく、検証用コピーの防御を壊したときに想定した失敗が発生するかを確認する。

- 親IDの取得後フィルタを外す：混在・誤成立・エラー混入・親ID確認の4テストが失敗する。
- 検索値を単一文字列へ戻す：検索形式のテストが失敗する。

一時ファイルだけを変更し、製品コードは変更しない。構文エラーでテストが落ちたことを検出成功と扱わず、構文が正しいことと失敗したテスト名まで確認する。

`.github/workflows/notification-checks.yml` に同じコマンドを登録している。notification配下またはワークフローの変更時にpush / pull_requestで起動し、手動実行もできる。CIはNode.js 22、ローカル確認はNode.js 23.11.0。CIは単体テストまでであり、Dockerの実更新は自動実行しない。

ブランチ保護でCIを必須にする設定は変更していない。自動チェックがあることと、GitHubが未成功のマージを禁止することは別である。

## 4. 仕様とテストの対応

| 仕様 | 自動テストの代表例 | 実環境の確認 |
| --- | --- | --- |
| 通知IDの独立性 | 別通知IDで同じパターン1を使ってもN001だけ成立する | 6条件を各3件に分離 |
| 誤成立の防止 | 別通知IDの条件で自ルールを誤って成立させない | 判定ごとのログを確認 |
| エラーの所属範囲 | 別通知IDの不正なFROM_TOを自ルールの評価に含めない | 実例外の所属を必要に応じて追加確認 |
| API結果の再確認 | 条件検索は親IDを配列として指定し、取得後も完全一致で絞り込む | リンク選択式列でitems.Getを確認 |
| FROM_TO | 指定4ケース、空白、先頭ゼロ、不正値 | 1.4.23.3で12シナリオ |
| IN / NOT_IN | 複数値、完全一致、空白、先頭ゼロ、空欄、不正設定、非トリガー | 1.4.23.3で26シナリオ |
| AND / OR | 同一パターンAND、別パターンOR | 複数条件・パターンの実更新 |
| 宛先 | To/Cc/Bcc、重複、To不足、メール形式 | ダミーの組織・宛先を参照 |
| 送信 | 送信無効、成功・失敗モック | OutgoingMails 0件。実配送未検証 |

## 5. 実環境で必須にする構成

検索・マスター関連付け・条件判定を変更するPRでは、単体テストに加えて次の両方を確認する。

| 親ID列ClassA | ルール | パターン | 目的 |
| --- | --- | --- | --- |
| 自由入力 | N001とN999の2ルール | 両方に1、N999に2 | 基本の検索とルール分離 |
| リンク選択式 | 同じ2ルール・同じ6条件 | 同上 | 列設定依存の検索挙動を確認 |

テストデータは [DESIGN.mdの具体例](DESIGN.md#9-条件設定の具体例) と同じ6件とする。親列には表示名N001 / N999ではなく各ルールの内部ResultIdを保存する。入力はstatusが0000→0100、denatsuが60kVとし、N001が成立、N999が不成立になることを確認する。

この2構成は2026/11/05にPleasanter 1.4.23.3 / PostgreSQL 16で実測した。自由入力では旧コードでも各3件に分離されたが、リンク選択式では旧コードは各6件を取得した。修正版は両構成で各3件、N001のみ成立した。

## 6. 実更新検証の手順

1. 本番・既存の作業データから分離した検証環境を用意する。バージョン・DB・ボリューム・ポートを記録する。
2. 通知ルール・条件・対象・組織・メール設定の検証テーブルを作る。条件の親ID列をリンク選択式にする場合は、通知ルールのサイトを参照先に指定する。
3. N001とN999、および具体例の6条件を作成する。所属を内部IDで確認する。
4. テスト用コピーにだけ検証サイトIDを適用する。更新前と更新後のSSに本体と対応する関数呼び出しを登録する。SEND_ENABLED=falseを確認する。
5. 必要ならcontext.Logをlogs.LogInfoへ変更して永続ログを取得する。このログ用変更を製品変更と混同しない。
6. 0000→0100、電圧60kVの更新を実行する。候補ルール、ルールごとの条件数と所属、成立結果、生成された通知内容を確認する。
7. 自由入力とリンク選択式を切り替えて同じ検証を行う。
8. 各ルール3件、N001のみ成立、送信なしを確認する。APIの200だけを合格基準にしない。
9. 修正前コードで問題が再現することと、修正版で解消することを比較する。
10. 使用コードのコミット・ハッシュ、入力、列設定、API応答、ログを保存する。

実環境を作れない場合は「実製品未検証」と記載する。単体テストの成功をその代わりにしない。

## 7. PRの確認票

- [ ] 変更する仕様と維持する仕様を明記した。
- [ ] 仕様書、コード、テストのルール境界が一致している。
- [ ] 単体テストと、防御処理を外した場合の検出確認が成功した。
- [ ] 検索に関わる変更では自由入力・リンク選択式の複数ルールを実更新で確認した。
- [ ] 異なる通知IDで同じパターン番号を再利用した。
- [ ] 失敗ケースは修正前で失敗、修正後で成功する。
- [ ] 送信APIのモックと実メール配送を区別した。
- [ ] 実施したこと・未実施のことをPR本文に分けた。
- [ ] 実行コードを変更した場合はモジュール先頭の変更履歴を更新した。

## 8. 今回の自動化の限界

このCIは同じ不具合の退行を検出するが、全てのPleasanter設定差を再現するものではない。Docker統合テストのCI化は未実施であり、上記の実更新手順を該当変更の必須確認にする。ブランチ保護や実メール配送を含む自動化は別途実装・確認が必要。
