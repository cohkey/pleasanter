# 通知条件混在の原因分析・検証見逃し・再発防止

作成日：2026/11/05
対象：通知IDが異なる条件を一緒に評価した不具合。修正PR #20。

## 1. 結論と責任

テーブル設定ミスではなく、スクリプトの不具合であり、私が行った検証・レビューの不足で見逃した。ユーザーが設定したN001とN999、同じパターン番号1は正しい設定である。

テストコードは実在し、実行もした。しかし、そのテストは今回の条件混在を検出できる構成になっていなかった。「テストが通った」は事実でも、通知ID間の独立性まで検証できたかのように伝えた点は不適切だった。

## 2. 発生したこと

通知IDをリンク選択式にしたテーブルでは、旧getNotificationConditionsのClassAに単一文字列とExactMatchを指定した検索で条件が絞られず、全6件が返った。取得後にClassAの再確認がなく、evaluateConditionsはパターン番号だけで分類した。そのためN999の条件がN001に混入した。

実行時の入力はステータス0000→0100、電圧60kV。正しくはN001が成立、N999が不成立である。

| 実測 | 旧コード | 修正後 |
| --- | --- | --- |
| N001で評価した条件数 | 6 | 3 |
| N999で評価した条件数 | 6 | 3 |
| N001の判定 | 不成立 | 成立 |
| N999の判定 | 不成立 | 不成立 |

Pleasanter 1.4.23.3の分離Docker環境にリンク選択式の列と同じ6条件を作り、この前後差を再現した。利用先の全データや過去の通知漏れ・誤通知の件数は調査していない。

## 3. なぜスクリプトのバグになったか

1. **APIの検索指定が列設定に合っていなかった。** 自由入力の列での挙動を、リンク選択式の列にも当てはめた。
2. **取得結果を信頼しすぎた。** 「このルールだけ取得できるはず」という前提で、親ルールIDの一致確認を省いていた。
3. **重要な境界が明文化されていなかった。** パターンの単位は親ルールIDとパターン番号の組合せだが、その境界を取得と評価の間で保証していなかった。

写真転記版にもこの不具合は含まれていたが、原本にあることは見逃しを正当化しない。提示された別の初期版には取得後の親IDフィルタがあり、写真版や通知対象取得処理との差を確認すべきだった。リファクタリング時に原本の動作を維持することと、業務仕様が正しいことの確認を分けるべきだった。

FROM_TOの比較計算が今回の直接原因ではない。複数ルールを評価したことで、既存の取得境界の問題が表面化した。

## 4. テストを書いていたのになぜ見逃したか

| 検証 | 実際に確認したこと | 抜けていたこと |
| --- | --- | --- |
| 初期のNode.jsモック | 指定した条件でモック自身が正しく絞り込む状況での判定 | Pleasanterが余分なレコードを返す場合。モックが実製品の契約検証の代わりになっていた |
| 最初の実環境検証 | 主に単一の通知ルールと自由入力の親ID列で一連の処理が動くこと | 複数ルール、同じパターン番号、リンク選択式の親ID列の組合せ |
| 原本との比較 | 処理・ログ・呼び出しが元のコードと一致すること | 原本自体が持つ不具合。元と同じことは正しい仕様の証明にならない |
| FROM_TO追加時 | 比較値、前後値、AND/OR、1.4.23.3の実行 | ルール境界と列設定を組み合わせた検索の再確認 |
| 件数による報告 | テストが実行され成功した数 | その数で何の業務上の不変条件を保証できたか |

単体テストでモックを使うこと自体が問題なのではない。モックで内部ロジックを確認する検証と、実製品で検索の意味を確認する検証を分けず、不足している後者の範囲を報告で明確にしなかったことが問題だった。

## 5. 説明時の誤り

最初のログを見た時点で、N001とN999の両方に同じ6件が渡っていることを優先して調べるべきだった。先に「同じパターン内で条件が矛盾している」と説明し、ユーザーの設定に問題があるように伝えたのは誤りである。

今後は、表示されているテーブル上の所属と、コードが実際に取得・評価した所属を分けて確認する。確定した事実と未確認の推測を区別し、設定ミスと断定する前に親IDと取得結果の対応を確認する。

## 6. 修正と実施済み対策

| 対策 | 状態 | 確認内容 |
| --- | --- | --- |
| 検索値をJSON配列文字列、検索方法をExactMatchMultipleへ変更 | PR #20で実施済み | リンク選択式の親ID列で各ルール3件を取得 |
| 取得後にも親ルールIDを完全一致確認 | PR #20で実施済み | 検索が余分な条件を返しても評価へ渡さない |
| 別ルール混在の回帰テスト4件 | PR #20で実施済み | 誤不成立・誤成立・別ルールの設定エラー混入・検索形式と再確認 |
| 旧コードでテストが失敗することを確認 | 実施済み | 4件とも旧コードで失敗し、修正版で成功 |
| 実製品で同じ列設定・6条件を使った前後比較 | 実施済み | 1.4.23.3でN001のみ成立を確認 |
| 業務仕様・境界・例外・未検証事項を設計書に明記 | この変更で追加 | DESIGN.md / TESTING.md |
| PR時の単体テスト・防御処理を外したコードでの検出力確認をCI化 | この変更で追加 | notification-checks.yml。実行結果はPRのChecksで確認 |

最後のCI追加はローカルで構成した時点とGitHub上で実行済みの状態を同一視しない。PRのChecksに実行結果が出るまでは「自動実行を確認済み」と報告しない。

## 7. 今後の変更で必須とする確認

- 検索・親子関連・条件評価を触る変更では、自由入力とリンク選択式の親ID列を別の実環境ケースとして確認する。
- 同じパターン番号を使う複数通知IDを必須データにし、ルール単位の条件集合と結果を検証する。
- 正常に絞られる場合だけでなく、検索結果が余分・空・型違いの場合も確認する。
- バグ修正時は、変更後の成功に加えて、回帰テストが変更前の不具合を検出できることを確認する。
- テスト結果はケースと保証範囲で説明する。Node.js、ClearScript、実DB検索、メール配送を分ける。
- 仕様書・コード・テストの不変条件を一致させ、変更時は同じPRで更新する。

詳細な実行手順・必要な証跡は [TESTING.md](TESTING.md) に記載する。

## 8. まだ自動化・確認していないこと

- CI上でPleasanterとPostgreSQLを新規作成し、列設定別の実更新を行う統合テストの自動実行。
- GitHubのブランチ保護によるCI成功必須化。今回設定は変更しない。
- 実SMTP、ユーザIDからの送信先解決、実メール配送、ブラウザ画面操作。
- 利用先における過去の通知漏れ・誤通知の調査。
- 他のマスター参照に対する全列設定・大量データ・ページングの網羅検証。

今回と同じ取得境界の退行は自動回帰テストで検出する。一方、実製品の設定差まですべてモックで保証できるわけではない。該当変更では実環境の組合せ検証を実施し、実施できない場合は未検証と明記する。
